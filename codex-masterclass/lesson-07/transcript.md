## 01 · Debugging starts with a contract

Clara here, the AI assistant at Orbix, reading lesson seven of Hector's class. Northstar Workshops now needs a small capacity checker for its local practice page. The workshop has twenty seats. The checker receives confirmed seats and seats requested, then determines whether the request fits. Everything remains a simulation: there is no backend, no real reservation, and no collection of personal information. Our goal is to repair behavior without replacing the surrounding project. The business contract comes first. Capacity is twenty. Confirmed seats must be a whole number between zero and twenty. Seats requested must be a nonnegative whole number. Remaining seats equal capacity minus confirmed seats. A request fits when it does not exceed the remaining seats. Zero requested is valid and changes nothing. GPT-6 Astra can reason about this contract and propose a correction when available. Tools inspect files, edit the implementation, and execute tests. The model saying the function looks correct is not a test result. By the end, you will have a reproducible defect, a focused patch, and evidence tied to the actual implementation.

## 02 · Reproduce before repairing

Begin with a concrete failure report. Suppose the illustrative broken checker accepts a request for twenty-one seats when none are confirmed. Expected behavior is rejection because only twenty seats remain. Record the input, expected result, actual result, and the command or page interaction that produced it. This gives the investigation a stable target. Ask Codex to read applicable guidance and locate the capacity calculation before making changes. If the practice files include a Python unittest suite, inspect its names and setup instructions. Run the documented command from the correct folder. A failure to import the module may mean the command ran from the wrong directory; it does not automatically identify a business logic defect. Keep the initial report short enough to reproduce. Do not paste every unrelated log from the project. The useful evidence is the failing case and the path to the code that handles it. If your starter does not exhibit the illustrative failure, describe the actual behavior instead of claiming the example occurred.

## 03 · Work the arithmetic by hand

Before reviewing code, calculate several answers yourself. With capacity twenty and confirmed seats zero, remaining seats are twenty. Requests of zero and twenty fit; a request of twenty-one does not. With confirmed seats twelve, remaining seats are eight. A request of eight fits and a request of nine does not. These examples reveal why checking only against total capacity is wrong. A proposed implementation might subtract the requested seats before deciding what remains. That can mix two different quantities: availability before the request and availability after an accepted request. Give each quantity a clear name. In this lesson, remaining seats always means capacity minus confirmed seats before evaluation. If an accepted request is simulated, the potential new remaining value can be shown separately. No persistent reservation is created. At full capacity, confirmed seats twenty leaves zero remaining. A zero request is still valid under our contract, while one seat does not fit. Keeping these expected answers outside the implementation helps you detect code that merely agrees with itself.

## 04 · Reject invalid inputs explicitly

Capacity arithmetic is simple only after the inputs are valid. A request of negative one must not increase available seats. A request of two point five is not a whole seat. Confirmed seats cannot exceed twenty or be negative. These are invalid inputs, which should be distinguished from a valid request that simply exceeds availability. For a Python function, define whether you accept only integer values or also parse strings. A clean lab contract accepts integers and rejects booleans, strings, and fractional numbers at the function boundary. This matters because Python treats booleans as a kind of integer in some checks. The webpage may receive text from an input control, but it should validate and convert that representation before calling equivalent business logic. Ask Codex to preserve the starter's documented return or error format unless a change is necessary. Do not force a new API merely to match an illustrative snippet. Write down the expected invalid-input behavior so the tests can distinguish an intentional rejection from an accidental crash.

## 05 · Ask for the smallest useful patch

Use a focused repair prompt: Inspect the capacity checker and its tests. Capacity is twenty. Remaining seats equal capacity minus confirmed seats. Confirmed seats must be integers from zero through twenty; requests must be nonnegative integers. Reject booleans and fractional values. Fix the observed failure with the smallest relevant change, preserve the documented interface, and run the focused tests. Report the root cause and changed files. The phrase smallest relevant change does not mean hiding a defect with a special case for twenty-one. It means correcting the actual rule without rewriting unrelated behavior. If the code compares a request with total capacity, change the comparison to validated remaining capacity. If validation is missing, add it at the appropriate boundary. A weak correction might simply clamp every request to twenty, silently changing the user's input. Rejecting an invalid or oversized request makes the outcome understandable. Review the patch against the contract before accepting a green test result. The tests themselves can also contain incorrect expectations.

## 06 · Tests that could catch a real mistake

A useful test suite expresses the business contract independently of the function's internal steps. Start with confirmed seats zero and requests zero, twenty, and twenty-one. Then use confirmed seats twelve and requests eight and nine. Add a full workshop case and invalid inputs such as negative requests, fractional requests, and confirmed seats above capacity. For a strict Python integer contract, include a boolean case too. Each test should have a name that explains the behavior, such as test_request_equal_to_remaining_fits. Use the starter's documented API when making assertions. If it returns a structured result, check the relevant fields. If invalid inputs raise a documented exception, assert that exception rather than accepting any crash. A test that copies the implementation's formula without an independent expected answer may repeat the same mistake. The hand-calculated cases from the previous slide are your reference. Run the focused suite first, then the project's required checks appropriate to the change. Do not claim the suite passed unless a tool actually executed it successfully.

## 07 · Interpret failures instead of hiding them

Imagine the test runner reports that nine requested seats were accepted with twelve already confirmed. This is a behavior failure: only eight seats remain. The useful next step is to inspect the comparison and trace the values through the function. Increasing the expected result to match the broken implementation would erase the evidence instead of repairing the defect. Now imagine a different result: the test runner cannot import the capacity module. That is an execution or setup failure. Check the working directory, module filename, and documented test command before changing business logic. An unavailable Python runtime is another setup limitation that should be reported specifically. The same principle applies to a timeout or missing dependency. The agent should state what ran, what failed, and what evidence supports its diagnosis. After a correction, rerun the previously failing case and the relevant suite. An illustrative final result might be all contract cases passing, but your submission must use the actual count and command from your environment, not a number invented for the lesson.

## 08 · Review changes with Git

Git helps you see what changed and preserve useful checkpoints. In an existing repository, begin with git status to identify modifications already present. Ask Codex to distinguish those from its own edits. After the repair, inspect git diff for the relevant files and compare the result with the requested scope. A capacity fix should not unexpectedly rewrite the landing page's approved copy. A diff shows lines added and removed; it does not establish that the new behavior is correct. Combine it with the test evidence. Ask for a plain English explanation of any change you do not understand, especially dependency updates, file deletions, or altered input handling. If you choose to commit, stage the specific files that belong to this change. Avoid staging every modification in a shared workspace. Commit locally only within your authorized workflow; pushing to a remote or merging is a separate action. If the project is not already a Git repository, explain that limitation and use the provided files and test log without pretending a commit or branch exists.

## 09 · Use worktrees for independent changes

A worktree gives a Git repository another working checkout so independent tasks can edit separate copies of its files. Northstar could keep the capacity repair in one worktree while a separate task revises the agenda copy elsewhere. This reduces direct interference, but it does not automatically resolve conflicting decisions or make all tools independent. Worktrees share repository history and metadata. They can also interact with shared resources such as ports, databases, or external services. Two local previews still need compatible runtime setup. Before starting parallel work, record the starting branch or revision and assign a clear scope to each task. Do not give both tasks ownership of the same capacity function. When you bring changes together, inspect the combined diff and rerun the relevant checks against the integrated version. A test that passed in an earlier worktree does not prove the merged result works. Use the worktree controls available in your client, or the project's established Git workflow. Availability and exact controls vary; the core concept is separate checkouts with deliberate integration.

## 10 · Permissions and rollback are specific

A controlled change includes a controlled response when something goes wrong. If Codex requests permission, the request should identify the action, the reason, and the affected resource. Running a test that needs a particular dependency is different from granting unrestricted filesystem and network access. Choose the smallest permission that resolves the actual need, or use an available local alternative. Rollback also needs scope. If a patch introduces a problem, ask the agent to identify and undo its own relevant change while preserving preexisting edits. A broad reset can remove someone else's unfinished work. Reviewing the diff before reverting is especially important when several tasks share a checkout. For Northstar, an appropriate correction could restore one modified comparison and then implement the validated rule properly. An inappropriate reaction would delete the entire practice folder because one test failed. Keep a clear account of changed files, the current state, and checks that still fail. That record supports recovery and lets another person distinguish a repair attempt from a completed repair.

## 12 · Recap: evidence makes a repair reviewable

A reliable repair has a chain of evidence. The report identifies a reproducible symptom. The contract establishes the expected behavior. The investigation explains the cause. The patch corrects that cause within the agreed scope. Tests and review then establish what the changed version actually does. None of these steps can be replaced by a confident completion message. For Northstar, an illustrative handoff says the checker now compares nonnegative whole-number requests with twenty minus confirmed seats, validates the confirmed-seat range, and passes the recorded boundary checks. The actual handoff should include your command, result, changed paths, and unresolved limitations. Git records the change; worktrees help isolate independent work; neither replaces behavioral verification. Before moving on, explain why twenty requested seats can fit when zero are confirmed but fail when twelve are confirmed. Then explain why a negative request is invalid rather than simply a request that fits.
