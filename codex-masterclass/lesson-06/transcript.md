# Lesson 6: Build and test a small local workshop landing page

Narrated by Clara Moretti, the AI assistant at Orbix Automation Solutions. Written by Hector Diaz. Northstar Workshops is fictional; all examples are synthetic.

## 01 · A page with a job

This is Clara, the AI assistant at Orbix, narrating Hector's class. Lesson six. Northstar Workshops is our fictional business throughout this course. It teaches independent creators how to plan a useful workshop. Today you will turn a short brief into a small local landing page, then gather evidence that the page behaves as intended. All business details and outcomes in this example are illustrative. Nothing here represents a live customer, published campaign, or measured conversion result. GPT-6 Astra supplies reasoning and generates proposed content and code when available in your Codex environment. File tools write the code, a terminal runs commands, and a browser tool can inspect the page if one is connected. Selecting a model does not supply those tools or authorize publishing. Our deliverable is deliberately modest: one page with an audience statement, learning outcomes, a sample agenda, and a clearly labeled practice signup area. Success means a learner can understand the offer and use the page locally. A beautiful description of a website is insufficient; we need files, observed behavior, and an honest handoff.

## 02 · Turn the brief into acceptance criteria

Start by translating the business request into observable conditions. Northstar wants a workshop page for creators preparing their first educational session. The intended action is to explore a sample agenda and try a practice signup interaction. Because this is a local exercise, we will not collect real registrations or connect payment services. Our acceptance criteria say the page must contain one clear main heading, three learning outcomes, a short agenda, and a practice form with a visible label. The primary button must lead to that form. Empty required fields must not produce a success message. Any confirmation must explicitly say that nothing was submitted. Notice how each condition can be checked. Make it professional is a preference; the button reaches the signup section is a testable behavior. We also specify a simple implementation using HTML, CSS, and minimal JavaScript unless the existing project requires otherwise. That constraint keeps the exercise focused on understanding and verification rather than managing an unnecessary application framework.

## 03 · Read the workspace before building

Before asking Codex to create files, give it the folder that belongs to this exercise. Ask it to read applicable project guidance and inspect the relevant existing files. If the directory is empty, it can propose a small structure. If a project already exists, it should reuse established conventions and report any conflict with your brief. This read first step prevents a common beginner mistake: asking for a simple page and receiving a replacement application that ignores work already present. For Northstar, a reasonable new structure is index.html, styles.css, and script.js inside the workshop folder. Existing projects may need a different structure, so treat these names as an example rather than an instruction to overwrite files. Ask Codex to identify the available preview and verification commands before running them. A missing runtime is an environment limitation, not proof that the page is broken. Have the agent explain the smallest next step. Permission to build within one folder does not mean permission to edit unrelated directories.

## 04 · The copyable build prompt

Here is a prompt you can adapt: Build a local Northstar Workshops landing page in the workshop folder. Read applicable guidance and existing files first. Use the supplied brief. Include audience, three outcomes, agenda, and a practice signup form. Keep dependencies minimal. The main button must reach the form. Validate required inputs and show a confirmation that no information was sent. Do not publish. Verify the behavior and report changed files, checks, and limitations. This prompt combines a business objective with concrete implementation boundaries. It also prevents the phrase signup form from silently becoming a connection to a real mailing list. The agent can make ordinary design choices within the brief without asking you to approve every margin or color. If it encounters a consequential ambiguity, such as an existing form that sends data externally, it should explain that specific issue before changing the integration. You can then choose an explicit action. Avoid responding with unrestricted access just to remove the interruption; resolve the actual dependency instead.

## 05 · A worked content hierarchy

Consider this illustrative content order. The heading says Plan your first useful workshop. The opening sentence identifies independent creators who have an idea but need a teachable structure. Three outcomes promise a defined audience, a practical lesson outline, and a draft invitation. These are curriculum intentions, not guarantees of income or attendance. The agenda then shows three sample blocks: clarify the learner problem, build a short teaching sequence, and review a workshop invitation. A button labeled Try the practice signup leads to the form. The page also says Northstar Workshops is a fictional training example and no registration will be sent. A weak generated version might invent hundreds of happy customers or describe a payment option that does not exist. Correct it directly: Remove unsupported social proof and payment language; use only details in the brief. This is a useful review habit for entrepreneurs. Code can function perfectly while the offer contains misleading claims. Content accuracy belongs in the acceptance criteria alongside technical behavior.

## 06 · Make the interaction truthful

A practice form still needs coherent behavior. Ask for a visible email label, a required email field, and a submit button that makes the demonstration clear. Browser validation can catch an empty field and many malformed addresses. It does not prove that an address exists, belongs to the person typing it, or is eligible for a real mailing list. In this exercise, submission should prevent any network request and replace or accompany the form with a message such as Practice complete. Your information was not sent or saved. Avoid a message saying You are registered, because no registration system exists. Prefer a synthetic address such as learner@example.com during testing. The illustrative correction is small but meaningful: change a misleading success message and verify that the handler performs no external submission. Do not assume a local page cannot transmit data; scripts and form actions can still target external services. Ask Codex to inspect both the displayed text and the code path responsible for the interaction.

## 07 · Preview through available tools

Once files exist, preview the page using the setup appropriate to the project. A simple static page may be opened locally or served by an available local server. An established application should use its documented development command. Have Codex report the command and address it actually used, rather than guessing that a familiar port is correct. If browser tools are connected, ask the agent to inspect the rendered page and exercise its controls. If they are unavailable, you can open the page yourself and follow a short manual checklist. In that case, the agent should report that it inspected source code but did not verify browser behavior. That distinction is a sign of a reliable handoff. We are not showing a fictional live demonstration here. The expected Northstar outcome is illustrative: readable content, a button that reaches the form, and a practice confirmation. Your run must establish its own results. A preview process starting successfully proves that the process started; it does not prove that every interaction works.

## 08 · Test the visitor journey

Test the page in the order a visitor experiences it. First, read the heading and introductory sentence. Can you identify who the workshop serves and what they will produce? Next, activate the primary button and confirm that it reaches the practice form. Then try submitting an empty field, an invalid address, and a synthetic valid address. For each check, record an expected result and the observed result. For example, empty submission should remain on the form with a validation message; learner@example.com should produce the explicit practice confirmation. An illustrative test log might show the button passing but the confirmation text failing because it claims a real registration. Also inspect a narrow viewport and navigate with the keyboard. Look for clipped text, horizontal scrolling, invisible focus, and an order that makes the form difficult to reach. These checks are a useful starting point, not a complete accessibility audit. Ask Codex to preserve evidence of what was checked and avoid converting a limited review into a claim of universal compatibility.

## 09 · Fix one failure at a time

Suppose the primary button does nothing. A vague prompt such as improve the page invites unnecessary redesign. A better prompt says: The Try the practice signup button does not reach the form. Inspect its target and the form section identifier, make the smallest correction, and repeat that interaction check. Preserve the approved copy and layout. In an illustrative implementation, the link points to signup while the section is named register. Aligning the identifier fixes the immediate defect. The important lesson is the sequence: describe the symptom, inspect the cause, change the relevant code, and verify the behavior again. Do not report that this exact defect occurred in your project unless you observed it. After the focused check passes, briefly inspect nearby behavior, such as whether the form can still receive keyboard focus and submit its practice response. You do not need a complete new design review after every tiny correction. The amount of checking should reflect the change and the uncertainty it introduces, while preserving unrelated work.

## 10 · Read the diff as a business owner

You do not need to understand every CSS declaration to review this result. Start with the list of changed files and ask Codex to explain why each changed. Then inspect the visible content and the interaction code. Look for unexpected analytics scripts, external form destinations, new packages, or business claims that were absent from the brief. A useful review request is: Summarize the change in plain English, identify external requests and new dependencies, and show any remaining risks or unverified behavior. If the response says none, ask for the evidence relevant to the project rather than assuming a confident statement is sufficient. A request for permission should name the blocked action, its purpose, and its scope. Downloading a required package, accessing a specific directory, and publishing a site are different actions. Approving one does not approve the others. For this lesson, publishing is outside scope. The final artifact should be ready for local review, with any future deployment step described separately and left for an explicit decision.

## 11 · Exercise: deliver the local page

Now complete the Northstar page yourself. Use the build prompt, adapt the folder to your workspace, and preserve any existing project guidance. Keep all business examples fictional. Ask Codex to implement the page, run appropriate available checks, and explain what it could not verify. If browser access is unavailable, perform the visitor journey manually and record your observations. Your submission should include the page files and a short test log containing the primary button check, empty input check, synthetic valid input check, and a narrow layout check. Include one defect you corrected or one edge case you investigated and found working. Do not introduce a bug merely to manufacture a dramatic result. Evaluate the work against the original acceptance criteria. An attractive layout with a misleading registration message is incomplete. A functional form with an unclear audience statement also misses the brief. The exercise is complete when the business meaning and observed behavior agree, the page stays within the authorized scope, and another learner can reproduce your local preview.

## 12 · Recap: brief, build, observe, hand off

The repeatable pattern is brief, build, observe, and hand off. The brief establishes the audience, intended action, content, and constraints. The build converts those requirements into local files. Observation compares the running page with the conditions you specified. The handoff records the result clearly enough that someone else can continue without guessing what happened. For Northstar, a concise illustrative handoff says: Created the local workshop page with three outcomes, an agenda, and a practice form. Verified the main link and input behavior. No registration is sent. Browser checks were performed only if the report includes actual observations. Publishing and real signup integration remain separate work. Carry that discipline into the next lesson. When something fails, you already have a specific expectation and a reproducible check. Debugging becomes a controlled correction rather than a request to regenerate everything. Before moving on, explain the difference between a model proposing code, a tool writing it, and a browser establishing that it works. Those distinctions keep your completion claims grounded.
