# Lesson 9: Long-running work, delegation, and scheduled checks

Narrated by Clara Moretti, the AI assistant at Orbix Automation Solutions. Written by Hector Diaz. Northstar Workshops is fictional; all examples are synthetic.

## 01 · Give sustained work a finish line

Clara again, the AI assistant at Orbix, with lesson nine of Hector's class. Northstar Workshops now has several related artifacts: a local page, a capacity checker, and a review checklist. Bringing these together can take more than one short exchange. The answer is not simply to tell Codex to keep working forever. Give the task an outcome, constraints, and completion evidence that allow it to choose useful next steps. GPT-6 Astra can support sustained reasoning across a workflow when available, while tools perform the actual file operations, checks, and connected actions. Long-running execution, delegation, and scheduling are surrounding capabilities whose availability depends on the client and environment. A model name alone does not guarantee them. In this lesson, we will design a bounded launch-kit preparation task and a draft monitoring prompt. We will not create any actual scheduled task. The distinction matters: work happening now has a current execution context, while a future check depends on a saved instruction and an environment that can run it later. Both need an explicit finish line and an honest account of what remains blocked.

## 02 · Write a measurable long-running goal

A useful Northstar goal says: Prepare a local workshop launch kit containing the page, synthetic attendance analysis, a sourced brief, and a handoff. Read the project guidance first. Preserve unrelated edits. Use synthetic data only. Verify the page and calculations, identify source limitations, and finish when the required files and evidence are complete. Do not publish or send messages. This describes a result rather than an endless activity such as keep improving the launch. The agent can compare its current state with the deliverables and decide what still needs attention. If the brief lacks a workshop date, it can mark that decision as unresolved instead of inventing a date to appear finished. Where a supported goal feature exists, you can use it to pursue the measurable outcome. Otherwise, the same plain-language instruction can guide a regular task. Do not assume that writing the word goal creates a persistent background process. Ask the environment to report what is actually running and what completion or interruption means for that run.

## 03 · Use checkpoints that preserve decisions

For a task with several stages, maintain a short progress record in the working materials. Northstar's record might list the page as implemented, the calculation as awaiting validation, and the brief as missing one source. Include relevant file paths, verification results, and decisions already made. This helps a resumed run continue without repeating completed work. A checkpoint should be operational rather than a long diary. Record what changed, what was verified, what remains uncertain, and the next useful action. If an earlier test passed against an older version, name that limitation instead of treating it as evidence for every later edit. When steering the running task, keep the original objective visible. A message asking for status should not silently replace the launch-kit goal. A correction such as use only synthetic data should apply to the remaining work and trigger review of affected outputs. If execution stops because of a limit or unavailable dependency, the handoff should preserve enough state to resume. A saved plan is useful evidence of intent, but it is not proof that future execution is scheduled.

## 04 · Delegate work that is actually independent

Delegation is useful when parts of the task can proceed independently. For Northstar, one subagent could analyze a supplied synthetic CSV while another checks official sources for the brief. The main agent can maintain the overall requirements and integrate the results. This is different from asking several agents to edit the same landing page at once. Give each delegated task a bounded input, output, and ownership rule. The CSV analyst owns the analysis output, while the researcher owns the source notes. Neither should rewrite the page or modify the other's files. If a review agent only needs to inspect work, give it a read-only role. Use subagents when the current environment supports them; otherwise, run the same bounded steps sequentially. Do not present unavailable delegation as if it happened. Parallelism can shorten elapsed time for independent work, but every agent performs its own model and tool work. That can increase total token use. Delegate because the split improves the task, not because more agents automatically mean a better or cheaper result.

## 05 · Write a delegation contract

Here is a concrete delegation instruction: Analyze the supplied synthetic Northstar CSV. Own only analysis.md. Read the data definitions, validate rows, calculate totals and rates, and report formulas and limitations. Do not edit the page or source brief. Return the output path, key findings, and checks performed. This gives the worker enough autonomy to complete a useful piece while protecting adjacent work. A research worker could receive a parallel contract naming source-notes.md and requiring official URLs, claim support, and uncertainty. The parent then reviews both outputs before using them. A worker's summary is a handoff, not automatic proof that every claim is correct. For the analysis, the parent should reconcile totals and inspect surprising rates. For research, it should confirm that cited sources support the claims used in the brief. Keep returned findings concise so noisy extraction details do not overwhelm the main task. If workers disagree, resolve the disagreement against shared definitions and evidence. Do not merge incompatible assumptions merely because both agents reported completion.

## 06 · Integrate before declaring completion

Independent outputs can each look reasonable while contradicting one another. Suppose Northstar's page says the workshop has twenty seats, but a delegated analysis labels twenty-five as the capacity. Before integration, determine whether the CSV contains a different scenario or the analyst used the wrong definition. Do not silently choose whichever number makes the report look stronger. The parent agent owns this reconciliation. It should compare the audience, capacity, workshop description, and practice-only status across the kit. Source notes should support the claims actually included in the brief. Calculations should use consistent denominators and retain the synthetic-data label. If code changes arrive from separate worktrees, inspect the combined diff and run the relevant checks on the integrated version. A passing test in an earlier checkout is useful history, but the deliverable is the current combined result. Completion should mean that required outputs exist, their relationships are coherent, and the stated verification has actually occurred. If one component remains blocked, describe the partial completion and the specific missing dependency instead of calling the entire kit ready.

## 07 · Distinguish a running task from a scheduled check

A running task is working now. A scheduled check is an instruction to run later under supported scheduling capabilities. Northstar might eventually use a scheduled check to inspect a launch checklist each morning, but describing that idea in a lesson does not create a schedule. All scheduling examples here are drafts only. The runtime matters. A local scheduled task that needs project files requires the relevant computer, application, and project to be available. A web task cannot directly inspect an arbitrary folder on your computer. Connected tools and permissions also need to be available to the scheduled run, not merely familiar to the model. Choose whether a future check should return to an existing task with its context or start an independent run from a durable prompt. Use the current client's supported controls to make that choice if you later authorize scheduling. Do not assume identical interfaces across desktop, web, CLI, and IDE. First establish that the manual check works and that the environment can support the intended future execution.

## 08 · Draft a durable monitoring prompt

A monitoring prompt needs more than check this daily. For a draft Northstar example, specify the local launch checklist, a proposed weekday time, the America/New_York timezone, and a seven-day duration. Define what the check should inspect and what counts as an actionable change. Also specify that it must not edit files, publish, or send messages. A useful notification rule is to report a newly failed required check, a change from blocked to ready, or a dependency requiring your input. Stay quiet when the state is unchanged and non-actionable. The prompt should also stop after the defined period or when the launch review is explicitly complete. Include how the run should treat missing access: report the failure without interpreting it as a healthy state. Make clear that notification means reporting to you through the task's supported channel, not messaging workshop participants. Save or display this as a draft only. Creating the actual schedule would require a separate explicit request and verification of the available scheduling capability and environment.

## 09 · Test notifications before relying on them

Before scheduling, test the prompt manually against a few controlled states. In the first fictional Northstar state, the checklist is unchanged and all recorded requirements remain satisfied. The expected result is no new notification. In the second, the page check changes from passing to failing. The expected result identifies the new failure, its evidence, and the next decision needed. In a third state, the checklist cannot be read. That should produce an access-failure result rather than a claim that nothing changed. A fourth useful case repeats the same known failure; the prompt should avoid repeatedly presenting it as a new development unless its severity or required action changes. These are simulations of monitoring logic, not evidence that a background service has run. Record the inputs and expected outputs in a small table or checklist. If the prompt cannot distinguish these cases during a manual run, refine it before creating any schedule. Useful monitoring reduces the effort needed to notice meaningful changes; it should not generate a stream of identical status messages.

## 10 · Control usage with scope and cadence

Usage discipline begins with task design. Give Codex the relevant files and a bounded outcome instead of asking it to reread the entire project repeatedly. Request concise evidence summaries with paths to detailed outputs. Keep related work together, but start a fresh task for unrelated work so irrelevant history does not become part of every decision. Choose an available model and reasoning effort appropriate to the difficulty. Start with the default or lowest setting that produces a reliable result, then increase effort when unresolved reasoning needs justify it. Do not assume a particular model or setting is available to every account. Subagents add their own work, so avoid delegating a trivial transformation to several workers. Scheduling also multiplies usage. A daily checklist that changes weekly probably does not need minute-by-minute polling. Inspect actual account usage and current limits when available rather than estimating remaining allowance from message count. If a limit interrupts work, preserve a concise checkpoint and resume from completed artifacts. None of these habits requires treating context compression as a guaranteed money-saving technique.

## 11 · Exercise: design a bounded workflow

Your exercise is to design the Northstar launch-kit workflow before running it unattended. Write one measurable goal with deliverables, constraints, and completion evidence. Then write two delegation contracts for independent pieces, such as CSV analysis and source review. If subagents are unavailable, describe the sequential fallback and keep the same ownership boundaries. Next, draft a scheduled-check prompt. Include a source, proposed cadence, timezone, duration, notification rule, and stop condition. Label it draft only and do not create a schedule. Test its logic manually against unchanged, newly failed, and inaccessible source states. Record what should happen in each case and whether the draft produces that outcome. Your submission should also include a short usage rationale. Explain why the work benefits from delegation, why the proposed cadence fits the source, and what evidence would justify changing model effort. Finally, name any specific permissions a real scheduled run would require. A broad request for unrestricted access is not a substitute for identifying the source and operations needed by the workflow.

## 12 · Recap: autonomy needs boundaries and evidence

Long-running work becomes manageable when the agent can identify the finish line and preserve the decisions needed to reach it. Delegation becomes useful when workers own independent outputs and the parent verifies the combined result. Scheduled checks become trustworthy when they have a tested prompt, an available runtime, and clear rules for notifications and stopping. For Northstar, the intended outcome is a coherent local launch kit with supporting evidence. The monitoring example remains an unscheduled draft. It describes how a future check could report new failures or readiness changes without repeatedly notifying you about unchanged state. Missing access remains visible, and messages to other people remain outside the authorization. Before moving to the capstone, explain who reconciles conflicting numbers from two subagents and what happens when a scheduled source cannot be read. Then identify the exact evidence that would let the launch-kit task stop. These answers matter more than keeping an agent busy for a long time. Productive autonomy means completing the authorized work, preserving its limits, and making the result easy to inspect. This is Clara, narrating for Hector Diaz and AI Auto Base.
