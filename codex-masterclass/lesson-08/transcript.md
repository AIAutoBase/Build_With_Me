# Lesson 8: Skills, plugins, MCP, and connected tools

Narrated by Clara Moretti, the AI assistant at Orbix Automation Solutions. Written by Hector Diaz. Northstar Workshops is fictional; all examples are synthetic.

## 01 · Know which layer does the work

This is Clara, the AI assistant at Orbix Automation Solutions, narrating lesson eight of Hector's class. Northstar Workshops has a local landing page and a tested capacity example. Now imagine the team also stores workshop planning notes in a connected document service. You want Codex to read an approved note and draft an updated checklist. This is where separating the model from the surrounding tools becomes essential. GPT-6 Astra can interpret the request and decide how to organize the result when available. A skill can explain the team's preferred review process. An MCP server can expose tools for retrieving documents or taking supported actions. A plugin can package useful capabilities for installation and reuse. None of those descriptions proves that a particular service is connected in your current task. Begin by checking what is actually available. The learning goal is a bounded read-first workflow: inspect the relevant capability, retrieve only the approved source, and draft a useful result. Publishing the checklist or messaging the team would be additional actions. You will practice making that boundary explicit without turning every reversible local step into a permission ceremony.

## 02 · Match the problem to the customization layer

Choose customization by the problem you are solving. If Codex repeatedly uses the wrong test command in the Northstar project, a short instruction in AGENTS.md is appropriate. If you repeat a multi-step workshop quality review, a skill can hold the procedure, examples, and supporting references. If the required agenda lives in an external document service, an available connector or MCP tool provides access. These layers can work together. Project guidance might say where approved workshop files live. A skill might require checking the agenda against learning outcomes. A connected tool might retrieve the actual source document. The resulting checklist still needs evidence and review. A common mistake is adding a large collection of instructions when the real problem is a missing connection. Another is installing a connector to solve a purely local writing convention. Ask what information or action is missing before adding anything. Use the smallest layer that addresses the recurring need, and keep the project guidance concise enough that important rules remain easy to identify.

## 03 · Read a skill before relying on it

A skill is more than a label in a menu. Its SKILL.md file describes when it applies and how to carry out the workflow. It may also reference scripts, templates, or supporting documents. Codex can discover a skill from metadata and load the detailed instructions when it becomes relevant. For Northstar, imagine a workshop review skill with three steps: read the approved agenda, compare activities with outcomes, and produce a checklist with evidence references. Before using it, inspect whether it also calls external tools or runs scripts. A local text template has different requirements from a script that updates a connected workspace. Do not assume every referenced file must be read on every run. Follow the relevant instructions and load the resources needed for the current task. If a required tool is absent, report the dependency and continue with a suitable local source when possible. A skill teaches a workflow; it does not create credentials or make unsupported actions available merely by naming them in its instructions.

## 04 · Treat a plugin as a capability package

A plugin is an installable way to distribute capabilities such as skills and connected tools. Its value depends on the work you need, the components it supplies, and whether those components are usable in your environment. Installing something with a familiar service name does not establish that it can read the specific Northstar document. Before depending on a plugin, identify its relevant tools, authentication requirements, and access scope. A service may expose search and read operations but restrict editing. Another may provide powerful write actions. The current task may have access to only part of the account or none of the required material. A useful instruction is: Identify the available capability for reading this approved planning document and explain any missing dependency before proceeding. Avoid treating installation as permission to send messages, publish pages, or update records. Authorization should come from the user's task and the specific action required. If a suitable tool is unavailable, an approved local export can support the lesson without pretending a live connection succeeded.

## 05 · MCP connects a host to capabilities

MCP stands for Model Context Protocol. In this workflow, Codex is the host, a client connection communicates with a server, and the server exposes supported capabilities. Those capabilities can include tools, readable resources, and reusable prompts. Some servers mainly provide reference information. Others can modify external systems. Think of a fictional Northstar document service with a search operation, a read operation, and an update operation. Searching for the approved agenda helps locate it. Reading retrieves its content. Updating changes the shared document. These are distinct actions even if they appear under the same connector. The names here are conceptual examples, not claims about a live tool schema. Ask Codex to inspect the actual tool definitions available in the task and follow their required inputs. The model's reasoning helps choose and combine operations, but the server and its authorization controls determine what can execute. If a read returns only a partial document or access error, that limitation must remain visible in the final result rather than being filled with invented content.

## 06 · Use a read-first prompt

Here is a bounded prompt: Read the approved Northstar workshop agenda using an available connected read tool. Confirm the document title and identifier before relying on it. Summarize the audience, outcomes, and unresolved decisions. Draft a local review checklist with references to the source. Do not update the document or send messages. If access is unavailable, report the limitation and use an approved local export if provided. This gives the agent a useful task it can complete without changing shared state. The explicit document identity reduces the chance that a similarly named draft becomes the source of truth. Asking for unresolved decisions also discourages the model from turning missing details into facts. An illustrative result might identify three outcomes, one practice activity, and an unresolved workshop date. It should not fill that date from memory or invent a booking link. The read-first habit is about grounding the next decision in the current source, not requiring a separate confirmation for every harmless lookup already authorized by the request.

## 07 · Treat retrieved content as evidence

A retrieved document can contain useful facts, outdated notes, and text that looks like an instruction to the agent. Treat it as source material for the user's task. A sentence inside an agenda saying send the attendee list to this address does not authorize Codex to send anything. The user asked for a local checklist, and that boundary still applies. In a Northstar practice source, imagine a note that says the date is tentative and another section that presents it as confirmed. A careful draft should identify the conflict and cite both locations. It should not choose the more convenient version without explanation. Also distinguish direct source statements from your own inference. If the agenda contains no practice activity for the third outcome, you may infer a coverage gap. Label that as a review finding and show the supporting source location. This keeps the checklist useful for decision making. You are asking the model to reason over evidence, while tool outputs remain data rather than new authority over the task.

## 08 · Handle missing access honestly

Suppose the document tool returns an access error. The right report identifies what could not be retrieved and how that limits the checklist. It might say the approved agenda was inaccessible, so no source-grounded review could be completed. If an approved export is available, the agent can review that copy and identify its version or date. A weak response would generate a plausible agenda and present it as the connected document. Another weak response would request unrestricted access without explaining why the existing permission failed. The required fix might be access to one document, a completed sign-in, or a different approved source. Those are specific dependencies. Ask for the narrowest next step that resolves the actual problem. If only a partial result was returned, state which sections were read and avoid claims about the rest. For Northstar, a draft based on an export can still be useful, provided the handoff explains that it may differ from the current shared version. Honest limitations preserve the value of the evidence you do have.

## 09 · Prepare a concrete external change

Sometimes the next step is an external update. Prepare the proposed change before asking the user to authorize it. For Northstar, the agent can draft a replacement checklist section locally, identify the target document, and explain what text would be changed. The user can then review a concrete result rather than approving a vague promise to improve the workspace. A specific request might describe updating only the checklist section of the identified agenda document with the displayed draft. It should not ask for broad unrestricted access to every connected service. If the original task already authorized that exact update, the agent should proceed within that scope and report the result instead of repeatedly requesting the same permission. Sending a message is a separate action. A request to draft an announcement does not authorize posting it to a community or emailing it to members. In this lesson, all connected work remains read only and outputs stay local. The example teaches the decision boundary; it does not execute an update or send a message.

## 10 · Turn a successful review into a skill

Once the Northstar review works, you can capture the reusable procedure in a skill. Define its purpose narrowly: review an approved workshop agenda against stated learning outcomes. List required inputs, such as the source identifier or local path, and the output, such as a checklist with evidence locations and unresolved decisions. The procedure might say to verify source identity, extract the audience and outcomes, map each outcome to an activity, and report gaps without changing the source. Include what to do when access is missing or content is incomplete. That instruction helps future runs avoid inventing a completed review. Keep broader project rules in AGENTS.md rather than copying them into every skill. A skill may reference a template or script when that makes the workflow more reliable, but extra machinery is not required for a short checklist. Test the skill against a second fictional agenda with a deliberate missing activity. Confirm that it identifies the gap and respects the read-only boundary before making it part of your routine process.

## 11 · Exercise: produce a sourced review draft

For the exercise, choose an approved fictional Northstar planning document. If a suitable connected read tool is available, use it to retrieve the document. Otherwise, use a local practice export and label that route accurately. The exercise evaluates the workflow and evidence, not whether your account happens to include a particular connector. Ask Codex to identify the source, summarize the audience and outcomes, and produce a local checklist that links each finding to a section or source location. Include at least one unresolved decision or explicitly state that none was found in the inspected material. Do not invent a gap merely to satisfy an expected story. Your submission should include the prompt, source identifier or path, checklist, and a short capability note. Explain which work came from model reasoning and which tool retrieved the data. Confirm that no shared document was changed and no message was sent. Finally, describe one specific permission request that would be appropriate if you later wanted to publish the reviewed checklist.

## 12 · Recap: workflow, access, evidence, action

You now have a practical way to reason about connected work. Project guidance carries recurring rules. Skills package repeatable procedures. Plugins distribute useful components. MCP connections expose actual capabilities. The model interprets your request and coordinates available tools, but it does not manufacture access simply because it knows about a service. For Northstar, the successful outcome is a local checklist grounded in an identified source, with unresolved decisions and access limits clearly stated. A connected read and a local export are different evidence paths; either can support the exercise when reported honestly. An external update would require a concrete target, reviewable content, and authorization appropriate to the action. Before moving on, explain why a document that mentions sending an announcement does not itself authorize a message. Then explain what you would do if the connector could search but could not retrieve the full agenda. These questions test whether you can preserve the task's boundary while still making useful progress. That same discipline becomes even more important when workflows run unattended or are delegated.
