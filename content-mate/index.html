The core of the class

★
One node holds the wiring for all of them
lesson 3

⚙️ Setup is the only Airtable node with a base ID typed into it. Every other one — twenty-five of them — resolves its base and table from that node's output:

every other Airtable node
$('⚙️ Setup').item.json['Airtable Base ID']

And then the part that surprises people. Open the Airtable credential itself — the access token is not a stored secret, it is an expression:

the credential's token field
{{$('⚙️ Setup').first().json['Airtable Personal Token']}}

The credential reads the token out of the table rather than storing it. twitterapi.io and both ElevenLabs calls go further — they take their keys straight from Setup as header expressions, with no n8n credential at all.

The idea worth more than the workflow

Configuration is data, not settings.

A hundred and six nodes, one place to repoint. You move to your own Airtable by editing one node. You rotate a key by editing one cell.

Take this pattern even if you never run Content Mate. It is the transferable part.

Lesson 3 breaks it on purpose

Change the base ID to garbage, run it, read the 403, put it back. Watching the failure is how you learn where the wiring actually lives — and on a recording you can rewind it.

Which means the Setup table is as sensitive as a password manager

Most of the keys in this system live in Airtable cells, not in n8n credentials. That is what makes one-cell rotation possible — and it means anyone with access to that base has your keys. Treat sharing it accordingly.

Say the price out loud

$1.60 per four-second Veo clip. That is the single biggest line in the monthly cost, and it is optional — a four-second phone video of yourself does the same job for nothing. We show that path too.

Why the captions are the good part

ElevenLabs Scribe returns per-word timings, and the Create Ass code node builds the subtitle file from those. The captions are aligned to what was actually said, not estimated from word count. That is the difference between subtitles that track and subtitles that drift.

Why this cannot run on n8n Cloud

Six Execute Command nodes and ffmpeg inside the container. Cloud gives you neither. You also need N8N_DEFAULT_BINARY_DATA_MODE: filesystem — without it a render is held in memory and the container gets OOM-killed, which does not error in any way that tells you what happened. It just dies.

Nine platforms, one API

Blotato sits in front of X, Instagram, YouTube, TikTok, Facebook, LinkedIn, Threads, Pinterest and Bluesky. Nine nodes. Bluesky ships disabled.

Nine is a maximum, not a goal

Every one of those platforms decides on its own what automated posting it permits, and any of them can change that. Connect the ones you actually use. Posting the same clip to nine places is not a strategy, it is a footprint.

Approve or deny — your ten minutes a day

The Review view, the Schedule view, and buttons that call webhooks. Telegram tells you when something went out.

This is the part the system actually needs from you, and it is the whole reason it is safe to run. Nothing publishes that you did not look at.

Seeing it as a calendar

A list answers "what is queued?". A month grid answers "what is going out this week?" — and it can live in the calendar you already look at every day.

Airtable's Create table gets a Calendar view, coloured by status, showing what is queued and what already went out. From there it goes into Google Calendar or Apple Calendar — but not the same way, and the difference is not obvious until it has cost you.

Google refreshes a subscribed feed every 8 to 24 hours

Not configurable. No manual refresh button. Google throttles external calendar fetches and does not publish the interval.

Content Mate publishes three times a day. So a post going out this morning may not show up in Google Calendar until tomorrow — which looks exactly like a broken integration and is not one.

On Apple take the feed. On Google write real events.

You have to do Google authentication for this class either way — every avatar, music track and finished video goes into Google Drive, so the Cloud project, the consent screen and the OAuth client are required whether or not you ever add a calendar. Budget 20–30 minutes, one-off, free.

Once that is done the calendar is genuinely small: enable the Calendar API on the same project, add one credential using the same client ID and secret, add one node. GOOGLE-AUTH.md in the pack walks the whole thing.

And the one that breaks a week later

If you leave the Google OAuth app in "Testing" with External user type, Google expires your consent and refresh tokens after seven days. Content Mate runs on a schedule, so the Drive uploads and the calendar events simply stop — with nothing to tell you why.

Publishing the app to "In production" fixes it, costs nothing, and does not make anything public. It is step 6 of GOOGLE-AUTH.md and it is not optional.

The iCal link is a public, unauthenticated URL

Anyone holding it can read your content queue — your scripts and your schedule. Not your keys, but not nothing.

And you cannot lock it down: Airtable's own docs say a share link with a password or domain restriction stops working as an iCal feed, because the calendar app cannot authenticate. If the queue is sensitive, use the n8n path — it never creates a public URL.

Write the event after publishing, not before

A calendar entry for something that failed to post is worse than no entry, because you will believe it went out. The calendar should record what happened, not what was intended.

Want the queue visible too? Write it to a second calendar you can toggle off, prefixed [queued] against [posted].

It does not schedule anything — the timing lives in n8n's three triggers, and moving an event does not move a post. That is deliberate: a calendar that could silently re-time your publishing is one that can publish something at 3am because you dragged it while half asleep.

Full detail ships in the pack as CALENDAR.md, including which field to build the view on and what to put in each event.
