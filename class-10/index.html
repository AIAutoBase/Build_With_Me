Read this before class

Nothing in this class has been run against a live box yet. No file has been ingested, no conversion timed, no MinIO container started. The conversion time you will see quoted for a forty-page PDF is an estimate, and it is labelled as one everywhere it appears.

What *is* proven, on a real machine, is the zone system: every test filename resolves to exactly one zone, every attempt to say "all zones" throws, and a query scoped to two zones carries that filter in SQL rather than in JavaScript after the fetch. The installer runs that check on your machine before class.

The one command

curl -fsSL -o install.txt https://aiautobase.github.io/Build_With_Me/class-10/install.txt && claude "Read install.txt in this folder and follow it exactly, from the top."

Windows, in PowerShell:

Invoke-WebRequest -Uri https://aiautobase.github.io/Build_With_Me/class-10/install.txt -OutFile install.txt; claude "Read install.txt in this folder and follow it exactly, from the top."

It starts no container, sets no password, and runs no migration. It reports what it found and stops.

Four zones, and they are a column

Personal, business, clients, general.

They are one `zone` column with a check constraint, on one table, in one bucket. Not four folders.

Folders were the obvious design and they are wrong. A file in a folder can be copied into a second folder, and then two rules apply to the same bytes and nothing says which wins. The question this whole system exists to answer — *may this prompt read this file?* — has to have exactly one answer per file, and a column is how you get exactly one.

The cost is honest: moving a file between zones is an UPDATE, which is invisible unless you log it. So it is logged, in its own table.

The original is the record. The markdown is a derivative

The uploaded bytes go into object storage unmodified. The extracted markdown goes into Postgres.

If the extraction was bad, or the extractor improves, the markdown is thrown away and regenerated. The original never is, because it cannot be.

You have met this idea before. It is the same argument this series makes about the difference between a build output and the record of what somebody actually downloaded — and it cost somebody something to learn.

The object key is the hash of the content

Content addressing, not filenames.

Upload the same invoice twice and there is one object. Upload it under two names, into two zones, and there is still one object with two rows. Filenames are metadata — they are not identity, they are frequently scan001.pdf, and they arrive with accented characters that three layers of this stack each mangle differently.

The trade: you cannot look in the bucket and see what anything is. Accepted. The bucket is not a filing cabinet for humans; the dashboard is.

Conversion is a queue, not a request

The upload endpoint's job ends when the bytes are durable. It returns immediately, marked pending. n8n picks the row up and converts it.

A forty-page PDF must not hold an HTTP connection, and a conversion that fails must not look like a failed upload. Those are different problems with different fixes, and collapsing them means every OCR timeout gets debugged as a network issue.

Statuses: pending, converting, converted, failed, unsupported.

`unsupported` is a real outcome, not an embarrassment. Audio and video get a row, an object, and no markdown. Hiding them would teach you the system holds everything, which is false. A file the brain has but cannot read is a fact the dashboard should state.

OCR ships, and it ships flagged

Every OCR result is stored with its confidence and displayed with a visible marker — on the file row, in search results, and in the context handed to the model.

OCR is the one component here that fails by producing a confident, plausible, wrong artifact. A scanned invoice yields fluent text with the wrong numbers. It gets embedded, it gets retrieved, and the brain cites it. Nothing anywhere reports a failure.

An unmarked OCR result sitting next to a parsed-PDF result in the same search output is a lie by formatting.

The five traps

TrapWhy it costs time
1MinIO with no named volumedocker compose down -v wipes it. Everything comes back healthy and empty, and Postgres still lists every file. You will debug this as a permissions problem for an hour
2MinIO default credentialsThe quickstart's minioadmin works, so nobody changes it. With a published port that is a public file server holding client contracts
3Accented filenamesSurvives the browser, mangled by the multipart parser, mangled differently by the converter's shell call. Content addressing hides the damage — the file is fine, only its name is ruined — which is why nobody notices for a month
4The body parser eats a 200 MB videoExpress buffers the whole upload before your handler sees it. Two concurrent uploads OOM the container, and no error mentions upload size
5Confident OCR garbageFluent text, wrong numbers, no failure reported anywhere

What you can verify before class

node check-zones.mjs

Every test filename resolves to exactly one zone. Every invalid zone input throws — including "all", "ALL", "Personal", an empty string, an empty array and undefined. A query scoped to [general, business] carries the filter in SQL and its parameters contain neither personal nor clients.

It touches no database and uploads nothing.

Still undecided, and you get a say

Which converter. markitdown covers the Office formats in one Python dependency. pandoc plus pdftotext plus tesseract is three system binaries, each doing one thing, and more predictable when one of them fails.

Build prompt 08 is written as the comparison rather than the implementation, so this choice is made once, in class, with the trade in front of you.

What this class does not do

Nothing here scans a file for malware. Files arrive from clients. That is a fact this class states rather than letting you assume otherwise.

And deleting a file deletes the row, not the object. Your brain now has a retention policy, and you chose it by default rather than on purpose — the last two minutes of the hour are about that.
