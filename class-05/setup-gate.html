The parts only you can do

About ten minutes, and no new account. One of these is a probe you genuinely have to run rather than assume.

The one with Docker, n8n and Postgres — not necessarily the laptop in front of you.

1

This class summarises what your Class 2 classifier writes. If nothing is writing, you will build a digest that reports zero every morning and looks perfectly healthy doing it.

docker compose exec -T postgres psql -U brain -d brain \

If the newest row is weeks old, fix Class 2 before Wednesday. Nothing in this class can help with that.

2
The probe that decides half the class

The draft half of this class writes a reply into your Drafts folder using an IMAP APPEND. Can your server accept one?

"My provider supports IMAP" is not an answer

It tells you nothing about whether APPEND works on your account, into that folder, with the right flag. Three things have to be true at once and only one of them is on any feature page.

If your check for "can I write a draft?" is reading documentation, you have not checked anything.

The pack ships verify.sh, which probes it properly — connects, finds the folder, appends a throwaway with the \Draft flag, confirms it landed, and deletes it again.

It needs three variables for that one run:

for one run only — note the quotes on the password
export BRAIN_IMAP_HOST=imap.yourprovider.com
export BRAIN_IMAP_USER=you@yourprovider.com
export BRAIN_IMAP_PASS='...'
bash verify.sh
Then unset them
afterwards
unset BRAIN_IMAP_HOST BRAIN_IMAP_USER BRAIN_IMAP_PASS

These are for the probe and nothing else. Your real credentials live in the n8n credential, and that is where they stay. Nothing is written to disk.

ResultWhat it means
APPEND accepted, found, deletedYou are ready
Folder not foundYours is called something else — step 3
APPEND rejectedYour provider does not allow it. See docs/UPGRADE-gmail-api.md
It appeared as received mailThe \Draft flag was not set. Fixable, and the class covers it
3
What is your Drafts folder really called?

There is no universal name, and this costs people twenty minutes.

ServerUsually
Many IMAP serversDrafts
Courier / some cPanel hostsINBOX.Drafts
Gmail over IMAP[Gmail]/Drafts
Localised serversBorradores, Entwürfe…

verify.sh lists them and prefers the server's own \Drafts flag, which is the only answer that is not a guess.

Saved in this browser only, so it is still here on Wednesday. It never leaves your machine and this page makes no network requests.

Get it wrong and your drafts become invisible

Write to a name your server does not use and IMAP happily creates that folder. Your drafts are real, they are being written, and your mail client never shows you the folder they are in.

4
The timezone check
on the brain machine
docker compose exec -T n8n printenv GENERIC_TIMEZONE
date
A 7am schedule on a UTC container fires at 2am

Nothing about that looks broken. The workflow runs, the email sends, the logs are green — it just happens while you are asleep.

If GENERIC_TIMEZONE is empty it uses UTC. n8n reads environment variables when the container starts and never again, so setting it needs a restart.

5
Decide what you actually want at 7am

Not technical, and it decides whether you keep using this.

Bring this to the hour. We build it around yours, not around what is easy to query.

A digest you delete unread is worse than no digest

Because you are training yourself to ignore something your own brain sends you.

"Forty-one items processed" is how that starts.

Also decide: what time do you actually read email? If it is 9am, do not send it at 7am.

One thing to expect on day one

Your digest will always send — even when there is nothing to say

An email that reads "nothing came in overnight" is not noise. It is the heartbeat.

A digest that only speaks when it has news is indistinguishable from a broken one. Without the empty one, silence is ambiguous — and you cannot tell a quiet week from a workflow that died three weeks ago.
