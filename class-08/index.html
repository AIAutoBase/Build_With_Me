You have seven weeks of work on one box, with no history, no versions, and no documentation. Change something, break it, and there is no way back. In three months you will not remember why any of it looks the way it does.

That is not a missing organ. It is a missing habit.

Classes 1 to 7 each added something to the brain. This one is aimed at you, and it is the cheapest hour in the series — git is free, local, and on most boxes already.

The one command

Run it on the machine your brain runs on — the one with Docker and n8n. Not your laptop, unless they are the same box.

Install the Class 8 pack

Terminal
curl -fsSL -o install.txt https://aiautobase.github.io/Build_With_Me/class-08/install.txt && claude "Read install.txt in this folder and follow it exactly, from the top."
bash

It downloads the pack, checks the checksum, and searches your history for secrets. Then it stops.

What the installer is forbidden from doing

It must not run git init, git add, git commit or git rm. Reading commands only.

An installer that helpfully staged everything would commit your .env — the exact failure this class exists to prevent — and it would take away the only decision the hour is trying to teach. Choosing what goes into a commit is the skill.

The repo gets built in class, by you, from P1.

Why it downloads a file instead of piping the prompt

The install prompt is 8,286 bytes. cmd.exe truncates a command line at 8,191 characters — silently, mid-word. Fetching to a file and pointing Claude at it is not stylistic; it is the only version that survives Windows.

13 files. The zip pins its timestamps, so the same sources always produce the same hash — a mismatch means the sources moved, not that the clock did.

Why now, and why before the terminal class

Class 9 puts a Claude/Codex terminal in your dashboard — an agent with shell access to everything you have built.

You want history before you hand an agent a shell.

When it breaks something — and it will — git diff is the way back.

That is the whole reason the boring-sounding class got scheduled ahead of the exciting one. It is worth saying out loud so it does not feel like filler.

The cold open

In the first four minutes I am going to delete a chunk of the dashboard, live, on purpose. Then put it back in ten seconds and explain nothing.

the whole demo
git diff                       # here is exactly what I destroyed
git checkout -- dashboard.html # and here it is back
That second command is the one that can lose work

git checkout -- throws away uncommitted changes with no confirmation and no undo. It is the only command in this hour that can cost you something. Read git diff first — that is what you are about to destroy. docs/UNDO.md in the pack covers the four undos and which one bites.

git is not GitHub

Local repo. No remote. No account. Nothing published.

What you getWhat it costs
Full undo, on every file, foreverNothing
A readable history of why things look like thisNothing
Diff before you commitNothing
Branches, if you ever want themNothing
An account somewhereNot required. Not used.

Your business documents' filenames never appear on anyone else's server, because nothing leaves the box. That is the same portability line the whole series runs on, and this is the cheapest class to hold it.

P1 · Track it 14–26 min

You end with: one commit containing your work, and .env nowhere in it.

StepWhat happens
git init -b mainThe folder becomes a repo. Nothing is tracked yet
The .gitignoreGoes in first, before anything is staged
git statusRead it. This is the moment to notice what you were about to commit
git add chosen pathsYou choose. Not -A
git commitThe first one
git ls-filesCheck .env is not in the list
The order matters and it is not obvious

.gitignore does not apply to files git is already tracking. Ignoring is for untracked files only. Commit .env once and adding it to .gitignore afterwards changes nothing — you have to git rm --cached it, and even then it stays in history.

Milestone

git log --oneline shows a commit, and git ls-files | grep .env shows nothing.

P1 alone is worth the hour. Stop here and you still have history, and you have stopped carrying your credentials around loose in a folder.

The .env beat 26–34 min

Four times across Classes 2, 3 and 4, I told you never to overwrite this file, because it holds the key that decrypts every credential you have saved.

I never once told you not to commit it.

Deleting it does not undo it

Commit .env a single time and it is in history permanently. Delete the file, add it to .gitignore, commit again — and you have a completely clean working tree while every earlier commit still contains the key. And so does every copy of that repo.

git status will never mention it again.

the question git status cannot answer
git log --all --full-history --oneline -- .env

Any output means it is in there. verify.sh runs this for you, plus a sweep for key-shaped strings across your last 200 commits — which catches the case .env checks miss: a key pasted straight into a workflow export.

If it is already in your history

Rotate what leaked. Do not rewrite history.

  • Rewriting changes every commit hash, so anything referencing them breaks
  • It does not help at all if anyone ever cloned or copied the repo — and a backup is a copy
  • It is fiddly enough that people get it half-right and believe they are done
And rotating the n8n key is not free

N8N_ENCRYPTION_KEY decrypts every credential n8n has saved. Change it and n8n cannot read any of them — they are still there, and unreadable. So: change the key, then re-enter every credential by hand. Budget an hour.

Do it anyway if the key is genuinely exposed to people you do not trust. If the repo has never left your machine, the honest risk assessment may be different — but make that a decision rather than an assumption.

The two files that stop it happening again

FileWhat it does
gitignore-templateExcludes .env before it excludes anything else, and un-ignores .env.example
env.exampleThe names, none of the values. This one is committed
The rule that outlives the list

Ignore lists go stale. This sentence does not: if it has a value in it, it does not go in git.

P2 · Version it 34–44 min

You end with: a feat: commit that takes 0.1.0 to 0.2.0, and a CHANGELOG that says why.

Suspicious that a version number on a folder only you use is ceremony? Fair. The honest case is three lines:

  • "It broke last Tuesday" is useless. "It broke in 0.4.2" is a place to look
  • A CHANGELOG answers "why does this look like this?" three months from now
  • It forces one sentence about intent per change — which is the actual value. The number is just the index
PrefixMeansBump
feat:A new capabilityminor · 0.1.0 → 0.2.0
fix:Something was brokenpatch · 0.1.0 → 0.1.1
perf: refactor: docs: chore:Faster / same / documentation / housekeepingpatch
feat!:Breaks somethingMAJOR · 0.1.0 → 1.0.0

The rule that matters more than the table: the prefix is a promise about what changed. If you cannot pick one, the commit is probably two commits.

the loop, from here on
git status --short              # what changed
git add <paths>                 # choose
./gcommit --dry-run "feat: ..." # what version will this be
./gcommit "feat: ..."           # do it
head -20 CHANGELOG.md           # READ IT BACK
Why the dry run exists

If any version string lives inside your repo — an app footer, an about screen, APP_VERSION — you must write the new number into it. Committing is what creates the new version. Writing the current one makes the footer stale the instant the commit lands, and fixing that produces another commit, which produces another version. Three releases in one afternoon, 2026-08-04.

Milestone

VERSION says 0.2.0, and the newest CHANGELOG section is under the title, on its own, with the older entries intact — because you opened the file and looked.

The five traps 44–50 min

Every refusal in the shipped gcommit is a real failure from this workspace, with a date and a cost. This is the segment that earns the hour.

#What went wrongIt now
1 git add -A swept another session's half-finished work into a commit. Three commits under the wrong message (2026-08-25) Never stages. You stage; it commits. Refuses on an empty index
2 A multi-line message silently lost its prefix — a feat: shipped as a patch, no error (2026-08-10) Refuses a multi-line message
3 Writing the current version into an app footer made it stale instantly (2026-08-04, three releases) --dry-run prints the version it will create
4 Docs-only commits bumped SemVer, restarting the treadmill (2026-08-05, two releases) Warns, and points at plain git commit
5 A CHANGELOG entry whose prose quoted the insert marker got a whole release section injected inside a bullet — two version headings, one buried mid-list (2026-08-18) Replaces only the first occurrence, and never inserts above the title
Trap 5 is the one to sit with

A dry run cannot catch it. It prints the version summary, not the diff — so it has nothing to say about a mangled CHANGELOG. The version number was perfect. The file was wrong.

Read the file. A tool that is careful about one thing and blind to the next is normal, not unusual — and that is the most teachable object in the hour.

The same rule applied to the pack itself

build-pack.py refuses to ship a gcommit that has stopped refusing. Testing that guard by breaking gcommit on purpose found two bugs in the guard: a substring matched inside a mutated flag, and comments about the refusals satisfied checks meant for the code. A guard that has never refused anything is just a print statement.

P3 · Document it 50–56 min

You end with: a README that someone else — or you in six months — could stand your brain up from.

Could a competent stranger, given only this repo, get it running without asking you anything?

Unlike "is it documented?", that question has an answer. And it is usually no.

#The four questions
1What is this? Two sentences. What it does, for whom. Not how
2How do I run it? Real commands, in order, from a machine that has nothing
3What do I need first? Accounts, keys, versions
4What breaks, and what do I do? The failures you have actually hit

Section 4 is the one that gets skipped and the only one anyone reads twice. Your own worst afternoons are the most valuable paragraphs in the document, and they are the first thing you forget. Mine them from your CHANGELOG and from the class TROUBLESHOOT files.

Two things that do not go in

No keys, tokens, chat ids, secret URLs, LAN addresses or personal paths. This file is going in git, and git remembers.

And nothing aspirational. If it is not built, it does not go in the README — "the inbox sort is set up but has never run against real mail" is a useful sentence. Silence there is a lie that costs somebody an afternoon, probably yours.

Commit it with plain git

git commit -m "docs: write the README", not gcommit. Documentation only, so no version bump — that is trap 4.

What this class does not do 56–60 min

git is not backup

It gives you history. It does not give you a second copy. A repo on a box that dies dies with it, along with every commit in it.

That is worth being annoyed about, and it is the honest next conversation. It is not solved by pushing to GitHub either — that is a different trade, and it means your filenames live on someone else's server.

Are you actually done?

Four things. VERIFY.md in the pack has the commands for each.

What passing does not mean

Not that your history is clean — that the checks found nothing. verify.sh looks at 200 commits and four key shapes. A password in a config file walks straight past it.

Not that the README is good — that it has four sections. Only the stranger test tells you, and you cannot run that perfectly on yourself.
