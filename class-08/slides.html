The line the whole hour turns on

You have seven weeks of work on one box, with no history, no versions, and no documentation. Change something, break it, and there is no way back.

That is not a missing organ. It is a missing habit — and in three months you will not remember why any of it looks the way it does.

Every class so far handed the brain something new to do. This is the first one that hands nothing to the brain at all. It is aimed at you, the operator, and the pitch is deliberately uncomfortable — because the alternative is finding out the hard way, mid-fix, that there was never a way back.

0:04 · why now, and why before the terminal

Next time, an agent gets shell access to everything you've built. You want history before you hand it a shell.

The next class puts a Claude or Codex terminal directly in the dashboard — an agent with shell access to the whole box. That is genuinely exciting, and it is also the reason this hour has to come first.

Teaching the terminal first would be teaching skydiving and mentioning parachutes afterwards.

What "no way back" actually meansWhen an agent with shell access breaks something — and it will, eventually, the same way any of us would — git diff is how you see what changed, and git checkout is how you get it back. Without a repo, there is no diff and nothing to check out. There is just the file, changed, with no record of what it used to be.

Nobody should walk out of this hour thinking the exciting class got postponed for a boring one. The ordering is the argument: a safety net installed after the thing it was meant to catch has already fallen is not a safety net.

0:08 · before you touch a terminal

Local repos. No remote, no account, nothing published.

  • No remote required, and none gets set up. This is a repository on your own machine and nowhere else.
  • Full undo, full diff, full history — with no account and no network call.
  • A member who does not want their business documents' filenames sitting on someone else's server never has to have them there.

This is the portability pillar held harder than anything since Class 6: your history lives exactly where your data already lives.

Say this now, before it needs saying laterLocal history is not backup. A repo on a box that dies, dies with it. That is named here on purpose, and again at the close — a safety net for mistakes is not a safety net for hardware failure, and pretending otherwise is how people lose everything twice.

It would be an odd way to end a series that has sold "your stack, your data, no rented dependencies" for six classes running by asking everyone to push their business up to somebody else's server in the name of version control. This class draws that line on purpose.

0:26 · the beat the hour is built around

Four times I told you never to overwrite this file, because it holds the key that decrypts every credential you have saved. I never once told you not to commit it.

That is not a memory problem. It is a gap nobody named out loud — until now.

Say this sentence to yourself before class: which file on your box holds a key, a password, or a token, and have you ever run a blanket git add in that folder without checking first? Whatever comes to mind is the exact thing this segment is for.

0:26 · what "permanent" actually means

Commit it once and it is in history forever. Deleting the file changes nothing.

  • Commit it a single time → it is in history permanently.
  • Delete the file and commit again → it is still in every earlier commit, and in every copy of the repo anyone has made.
  • git status going clean tells you nothing about what history already holds.
The fix is rotate, not rewriteIf it has already happened, the answer is to rotate the key — change the value everywhere it is used — not to try to rewrite history. Rewriting does not help once a repo has been copied anywhere, and a backup is a copy.

This is the sentence worth remembering after the syntax is forgotten: history remembers what status forgets. A clean working tree is not evidence of a clean past — only the history itself can tell you that, which is exactly what the preflight check searches.

The fix, live

A .gitignore that actually excludes it. An .env.example with names, no values.

TrackedNot tracked

The rule that matters more than the listIf it has a value in it, it does not go in git. Lists go stale; that sentence does not.

The build guard for this pack refuses to ship if the ignore file stops excluding the secrets file, or if the example file gains a real value. Both are easy to "tidy" into uselessness without anyone noticing until it's too late.

Two files, in the right order, before the first commit exists. That is the entire technical fix. The harder part is the habit of checking git status before every commit rather than after, and that habit is what step 6 of the first prompt is built to install.

P2 · Version it · why bother

"It broke last Tuesday" is useless. "It broke in 0.4.2" is a place to look.

  • A changelog is the answer to "why does this look like this?" three months from now, when you have forgotten.
  • It forces one sentence about intent per change — the number is just the index into those sentences.
  • For a folder only you use, this is a fair thing to be suspicious of. The honest case has to be made, not assumed.
Why the tool ships as a plain shell scriptMembers run boxes without a heavier shell environment installed, so the versioned-commit wrapper ships as ordinary, dependency-free shell script — same conventional-commit, SemVer, changelog behavior, running where members actually are.

Notice the order: the prompt asks the case to be made before a single tool gets installed. If the case can't be made honestly for a given folder, the right answer is to skip it there — ceremony that isn't earning its keep is exactly the kind of thing this series avoids.

P2 · step 2

Read the comment block before you trust it.

  • The script's own header lists five real failures, each with a date, that it refuses to repeat.
  • Reading that block before relying on the tool is the point — you should know what it is protecting you from, not just that it exists.
What it never doesIt never stages anything on your behalf, and it never accepts a multi-line commit message. Both refusals exist because both mistakes have already happened once, for real, in this same workspace.

P2 · step 4 · which prefix bumps what

The prefix is a promise about what changed.

PrefixMeaningBump
feat:a new capabilityminor — 0.1.0 → 0.2.0
fix:something was brokenpatch — 0.1.0 → 0.1.1
perf:same thing, fasterpatch
docs:documentation onlypatch
refactor:same behavior, different codepatch
chore:housekeepingpatch
feat!:breaks somethingMAJOR — 0.1.0 → 1.0.0

If you cannot pick one, the commit is probably two commits.

The table is the easy half. The rule underneath it is the part worth keeping: the prefix is not a label applied after the fact, it is a decision made before you write the message, and it forces you to know what you actually changed.

P2 · step 5 · the number it prints

A dry run prints the version it will create — not the one you have.

what the dry run actually printed0.1.0 -> 0.2.0 DRY RUN - nothing written

Index untouched. Nothing committed. Just the number the real run would produce.

Why that number matters more than it looksIf a version string lives inside the repo itself — an app footer, an about screen — it has to be written with the new number the dry run just printed, not the current one. Committing is what creates the new version; writing the current one just means the footer goes stale the instant the commit lands, and fixing that produces another commit, which produces another version.

This is the kind of trap that looks obvious once it's named and is genuinely easy to fall into otherwise — the natural instinct is to write down the number you can see right now, which is always one step behind the number that is about to exist.

A dry run cannot show you this. You have to read the file.

Which is exactly why the versioning prompt insists: read the changelog itself afterward. Don't just check the version number — check that there is exactly one new section, and that the old ones are still intact.

The dry run exists to protect the version number. It says nothing about the file the version lives in. Trusting a dry run to mean "the changelog is fine" is a small leap that this exact bug punished, in this exact workspace.

P2 · what "it worked" looks like

One new section. Under the title. The old one intact.

what running it produced--init: VERSION 0.1.0, CHANGELOG.md created (commits nothing - you do) --dry-run: 0.1.0 -> 0.2.0, nothing written real run: Committed 0.1.0 -> 0.2.0
Read the changelog properly, not just the version numberIs the new section at the top, under the title, and not above it? Is there exactly one new version section? Are the older entries still intact — no bullet split in half?

A docs-only change — touching only documentation, nothing else — gets a plain warning instead: everything staged is documentation, and the suggestion is to use an ordinary commit with no version bump at all.

The version number passing is necessary and not sufficient. The changelog file is the actual artifact people will read in six months; the number is just how they'll find the right entry in it.

Part 3 · the test this prompt is built around

Document it, for a stranger

Not "is it documented?" — that question has no answer and everyone says yes. Could a competent stranger, given only this repo, get it running without asking you anything?

3

That question has an answer, and for most folders on most boxes the honest answer going in is no. The point of this prompt is closing that gap rather than papering over it with a template.

P3 · four questions, in order, nothing else required

What is this. How do I run it. What do I need first. What breaks, and what do I do.

  • What is this? Two sentences. What it does, for whom — not how.
  • How do I run it? The actual commands, in order, from a machine that has nothing. Every one copy-pasteable.
  • What do I need first? Accounts, keys, versions — what has to exist before the previous step works.
  • What breaks, and what do I do? The failures you have actually hit, and the fix.
Ask, don't inventIf something's purpose is not obvious from the file, the agent asks rather than guessing. A confident wrong sentence in a README is worse than a gap, because you will believe it in six months.

Four questions, always in this order, and nothing else required. A README that tries to be a tutorial, a design doc and a changelog all at once ends up being none of them well; this one stays narrow on purpose.

P3 · step 3 · the section that gets skipped

Your worst afternoons are the most valuable paragraphs — and the ones you forget first.

  • Read the troubleshooting files from earlier class packs for real failures.
  • Look at what's recorded as fixed in the changelog.
  • Ask directly: what has gone wrong that took more than ten minutes?
What does not go in itNo keys, tokens, or URLs with a secret in them. No LAN addresses or personal paths — placeholders, clearly marked as placeholders. No screenshots of anything with a credential panel open. And no aspirational sections: if it is not built, it does not go in the README.

This is the section almost everyone skips, and the only one anyone reads twice. Writing it down while the memory is fresh is cheap; reconstructing it from nothing six months later, after you've forgotten exactly what went wrong, is not.

Before you need it

Git has a lot of ways to go backwards. You need four.

SituationCommandSafe?
Uncommitted changes you want gonegit checkout -- pathLoses work. No confirmation, no recovery.
Staged something by mistakegit restore --staged pathSafe. The file keeps your changes.
Last commit was wronggit reset --soft HEAD~1Safe. Commit disappears, work stays staged.
A commit already shared elsewheregit revert <commit>Safe. A new commit undoes the old one.

Finding what to go back to: git log --oneline, git show <commit>. "It broke in 0.4.2" gives you a place to start; "it broke last Tuesday" does not.

Three of these four are safe by design. Knowing which one isn't, and why, is worth more than memorizing all four commands — the dangerous one is also the one you'll reach for most often, because it's the one from the cold open.

The one from the cold open

git checkout -- throws away uncommitted changes. No confirmation. No undo.

look before you run itgit diff path/to/file # this is what you are about to destroy
If you're not sureCommit first. A messy commit you delete later beats work that no longer exists at all.
What NOT to reach forgit reset --hard throws away commits and uncommitted changes together — it is the one behind every git horror story. And rewriting history to remove a secret is never the first move: rotate the secret instead. Rewriting does not help once the repo has been copied anywhere, and a backup is a copy.

The command that made the cold open look effortless is the same command that can erase an afternoon of uncommitted work with zero warning. Both things are true about it, and only one of them gets demonstrated on stage.
