Read this before class

Nothing in this class has been run against a live box yet. No registry has been built, no module loaded, no migration ordered, no database role created.

What *is* proven, on a real machine, is the manifest validator: three real manifests validate, and seven deliberately broken ones are refused — a table declared outside its own prefix, a route mounted under another module's path, a manifest built for a host API we do not implement, a dependency on a module that is not installed, an unknown permission, and a two-module dependency cycle that names both modules. The installer runs that check on your machine before class.

The one command

curl -fsSL -o install.txt https://aiautobase.github.io/Build_With_Me/class-12/install.txt && claude "Read install.txt in this folder and follow it exactly, from the top."

Windows, in PowerShell:

Invoke-WebRequest -Uri https://aiautobase.github.io/Build_With_Me/class-12/install.txt -OutFile install.txt; claude "Read install.txt in this folder and follow it exactly, from the top."

It runs no migration, creates no database role, installs no npm package, and modifies no existing file. It scans for collisions and stops.

The question this class refuses

*Which features should the dashboard have? CRM, ERP, and so on.*

By now you have five tabs and a list of eleven more that would each be useful. Adding the sixth by hand takes an afternoon. Adding the sixteenth takes an afternoon and breaks two of the others, because by then nothing says what a tab is allowed to touch.

So the hour refuses the question, and the refusal is the class.

What a well-known 46-module dashboard actually teaches

It is easy to read forty-six modules as a feature list to catch up with. That is the wrong reading.

The valuable thing about forty-six modules is that the forty-seventh costs almost nothing. Nobody hand-wired forty-six tabs. There is a shape a module has, and once that shape exists, modules are cheap and the host stops being the bottleneck.

We ship three. Three is enough to prove the socket and few enough to resist the pull of rebuilding somebody else's product with a two-year head start.

A module is a folder with a manifest

modules/contacts/
  module.json      id, title, version, hostApi, routes, tables, zones, dependsOn, permissions
  migrations/      this module's tables, and only its own
  server/          its API routes, mounted under /api/m/<id>
  ui/              its React tab

The host reads every module.json at boot, validates it, orders the migrations, mounts the routes and renders the tab. A module that fails validation does not load, and the host says which one and why — it does not start half-configured.

The isolation contract, in one rule

Every table a module creates is prefixed with its id: m_contacts_*. The host grants that module a Postgres role that can reach its own tables and nothing else — enforced by the database, not by convention, because a convention is a comment and a comment does not stop a JOIN.

The cost is real. The Tasks module cannot join to Contacts. It has to ask, through a declared interface. That is inconvenient, and it is the entire reason a module can be deleted without a two-day investigation into what else was reading its tables.

A module declares the zones it reads, and cannot widen them

Class 10's four zones, one last time.

module.json carries a zones array. The host injects a search function bound to exactly those zones. A module never receives the unbound one, so it cannot construct its own query.

ModuleReads
Contactsclients, business
Tasksbusiness
Invoicesclients, business

Nothing ships reading personal. A module that declares it still loads — and the host logs a warning naming it. Personal is not forbidden. It is just never quiet.

Installing a fourth module from somebody else then becomes a question you can actually answer, because the manifest states what it wants and the host decides whether it gets it.

Three modules, chosen for their shapes

ModuleShapeWhy this one
ContactsA list with a detail viewThe CRM question everyone asks, at its smallest honest size
TasksA board with state transitionsA different data shape, and the only one with a workflow
InvoicesA document that renders and totalsMoney, formatting, and the module that must never be wrong

Three shapes, not three features. Somebody with a fourth idea has a template that fits it.

We are not building an ERP, and here is why

An ERP is accounting, inventory, payroll and tax — each with legal consequences that differ by country, each audited, each wrong in a way that costs money rather than time.

A weekend ERP that is 90% right is not 90% of an ERP. It is a liability with a nice dashboard.

What is genuinely better than a bad ERP: three small modules your brain can read, that answer the phone, sitting next to your real accounting software instead of trying to replace it.

The five traps

TrapWhy it costs time
1An unversioned registryEverything works until you share a module. Then somebody's host is a minor version behind and the failure is a white screen with a stack trace from inside code they did not write
2Migrations in whatever order the filesystem returnsWorks on your box for months, because your filesystem happens to return them in creation order. Breaks on a fresh install, on somebody else's machine, on a day you are not there
3One module importing another's code directlyOne line, it works, invisible in review. Six weeks later deleting a module breaks two others and nothing says why
4Porting all forty-sixNothing breaks. You spend three months rebuilding somebody else's product instead of running your own company with the one you have
5A module whose database role can read everythingIdentical behaviour to a correctly scoped one, forever, in every test. The scoping is only observable at the moment it would have mattered, and by then it did not

Four of those five are the same shape as every trap in this series: a silent failure that produces a plausible artifact. Trap 4 is the only one that costs nothing but time, and it is the most likely to actually happen.

What you can verify before class

node check-registry.mjs

Three real manifests validate. Seven broken ones are refused, each for the specific rule it breaks. The cycle pair is refused by name.

It loads no module code, mounts no route and touches no database.

What this does not protect against

  1. The frontend. Every module's React code runs in the same page as every other module's.

Nothing here stops a bad module reading the DOM of a good one. The word "isolation" in this class means the database, and it should not be stretched further.

  1. A dashboard connecting to Postgres as a superuser. Every grant becomes decorative. The

installer checks and tells you before class.

  1. More surface for the cockpit's agent. The socket makes adding things cheap, and cheap

is not the same as free.

What twelve weeks built

Reasoning, senses, memory, ears, voice, hands, a graph, a clock, history, a cockpit, a mouth, a phone number, and a socket.

What it still does not have: anyone but you. Every guard in this series protects the system from mistakes and from strangers. None of it answers what happens when a second person needs their own login, their own zones, and their own answer to what they are allowed to see.

That is a different series.
